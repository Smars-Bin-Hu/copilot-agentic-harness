# 提示模板

给人用。复制一段，把尖括号里的内容换成你的，发给 Copilot Chat。

你不用写命令，也不用先定级。agent 会用技能 `harness-my-task` 问你几个问题，再开任务。模板的作用是把最要紧的上下文一次说清：要做什么、改哪个仓库、知识库在哪、做到哪一步停。这样它少问、少猜。

## 标记

写在提示里任意位置，hook 会读。

| 标记 | 作用 |
| --- | --- |
| `[review]=1` | 这个任务的成果要通过 1 次独立检查才能回写。任务里写一次就够 |
| `[review]=2` | 要连续通过 2 次，每次换一个新的 reviewer。更稳，也更贵 |
| `[review]=0` | 关掉这个任务的独立检查 |

不写就是不查。1.1.0 之前的 `[verify]` 等于 `[review]=1`，`[no-verify]` 等于 `[review]=0`，还能用。`/l1`、`/l2` 不用再写了，写了也没有作用。

## 问一个问题（不开任务）

```text
<问题>。
范围：<仓库名>/<目录或文件>。
知识库：knowledge-base/，先读 knowledge-base/README.md，再按索引读 <domain 名> 相关的文件。
只回答，不改任何文件。
```

## RCA、设计、方案（成果存成文件，不改仓库）

```text
[review]=1
<要分析的现象，或要出的方案>。
范围：<仓库名>/<目录或文件>。
知识库：knowledge-base/，先读 knowledge-base/README.md，再按索引读 <domain 名> 相关的文件。
不改目标仓库。把结果写成 <RCA.md / DESIGN.md>。
先把你理解的需求写进 REQ.md 给我看，我确认后再做。
```

说明：

- 不想检查就去掉第一行。
- 你有需求文档、日志，等它开好任务后放进任务目录的 `REQ/`、`REF/`，再告诉它。
- 任务目录在 `.workspace/sandbox/tasks/<任务名>/`，名字由它起。

## 开发（要改目标仓库）

```text
[review]=1
<要做的改动>。
目标仓库：<仓库名>。要改的范围大致在 <目录或文件>。
知识库：knowledge-base/，先读 knowledge-base/README.md，再读 <domain 名> 相关的文件。
1. 先把你理解的需求写进 REQ.md，把计划写到 PLAN.md，然后停下，给我两个文件的链接，等我批准。
2. 我批准后，只改计划里列的文件，不动别的逻辑，不重构。
3. 做完独立检查，再 task promote --dry-run，给我 PROMOTE-PLAN.diff 的链接，等我批准。
验收：<必须实现的功能；哪里必须能看到数据；不能影响的已有功能>。
```

说明：

- 分支名默认是 `feature/<任务名>`，任务名里的 `-` 会变成 `_`。要别的，加一句：`分支名用 feature/<名字>`（字母、数字、下划线）。
- 两次批准都在你自己的终端：`harness task approve-plan`、`harness task approve-promote`。批准完回对话说“批准了”。
- 只要成果、不回写仓库：把第 3 步改成“做完 task diff，然后停下”。

## 接着做

换了会话，或隔了几天：

```text
接着做 <任务名，或一句能认出它的话>。告诉我做到哪了，然后继续。
```

不记得有哪些任务：在终端运行 `harness task list`。

回写之后还要再改一轮：

```text
任务 <任务名> 上一轮已经回写。还要改：<新的要求>。
开新的一轮，写新的 PLAN.md，停下等我批准。
```

## 改需求

直接说。它应该先改 `REQ.md`，再动成果。

```text
需求变了：<新的条件，或要取消的条件>。先更新 REQ.md，再告诉我要改哪些地方。
```

## 任务变大了

本来只是分析，现在要改仓库：

```text
这个任务要改目标仓库 <仓库名> 了。把它升到带 DEV/ 的那一档，写 PLAN.md，停下等我批准。
```

## 只检查

成果已经写好（你自己改的，或上一步做的）：

```text
[review]=1 <任务名> 的成果已经写好，不要改文件。做独立检查，把结论告诉我。
```

## 检查次数用完了

agent 会停下来告诉你最后一次的问题在哪。你在自己的终端选一个：

```bash
harness task review extend --checks 2   # 再给 2 次
harness task review waive               # 不查了，放行这一版
```

然后回对话说一声。

## 长任务：目标驱动

任务大、会跨很多天或多个 session 时才用。只有你能启动，日常任务不要用。它把中心思想、步骤清单和进度写进 `.workspace/goals/<目标名>/`，每步做完等你说“通过”。

新建目标：

```text
/generic-goal-driven 目标：<要做成什么>。
背景：<需求在哪、涉及哪些仓库或 domain>。
整体验收：<做到什么程度算完成>。
先问我不清楚的地方，再拆步骤。拆好后给我文件链接，等我确认再开始第 1 步。
```

换了 session 或隔了几天，接着做：

```text
/generic-goal-driven 继续
```

说明：

- 只有你在对话里说“通过”，步骤才算通过。
- 接着任务的会话写不了目标文件，要等 `task close` 之后再写。

## 什么时候用哪个

| 情况 | 怎么做 |
| --- | --- |
| 查一个东西，解释一段代码 | 直接问，不开任务 |
| RCA、设计、方案，要存成文件 | 说要做什么，它开一个中档的任务 |
| 要改目标仓库 | 说要改什么、改哪个仓库，它开一个全档的任务，计划和回写等你批准 |
| 想要独立的检查 | 加 `[review]=1`；重要的改动用 `[review]=2` |
| 跨很多天的大事 | `/generic-goal-driven`，每一步是一个任务 |
| 改 harness 自己（hook、策略、engine、agent、skill），读报告，查 harness 出错的根因 | admin agent，先在终端 `admin on` |
