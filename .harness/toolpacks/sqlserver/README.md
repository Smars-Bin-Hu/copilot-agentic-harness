# sqlserver: a sample tool pack (1.3.0)

A ready tool pack for SQL Server reached with `sqlcmd`: copy it, list your connections, and colleagues only type their own account in Get ready. The harness knows no connection type; SQL Server is one this pack brings.

## What is in it

- `toolpack.json`: its name, version (1.3.0: what an ETL test on DEV needs waits for the person instead of being refused: a drop or truncate of a table on DEV and IST, the body of a procedure, a string run as SQL, a `$(name)` nothing fills; `:setvar` and `-v` are filled in; more writes on the write list; 1.2.0: a call must name one connection's server (`pin`), other ways to a SQL Server are refused (`rules.json`), a `WHERE` that is true whatever the row holds does not count, a procedure, function or view is one statement to the end of its batch, the refuse list no longer teaches `DELETE ... WHERE`; 1.1.1: the long options of go-sqlcmd (`--server`, `--input-file`, `--query`, `--initial-query`, `--output-file`, `--trace-file`, `--database-name`) are read like `-S`, `-i`, `-Q`, `-q`, `-o`, `-d`; 1.1.0: the lists `reads`, `writes` and `refuse`, `-Q` judged as a text; 1.0.2: the skill's examples have no `-E`; 1.0.1: `open` rules, needs harness 1.7.38), and the program it needs (`sqlcmd`).
- `types/sqlserver.json`: the connection type. The fields of a connection (server name, port, database), two ways in (`windows`: a Windows account, held by the VS Code window the way `runas /netonly` holds it; `sql`: a SQL account, which sqlcmd reads from `SQLCMDUSER` and `SQLCMDPASSWORD`), the test of the way in (it asks the server who the session is), what sqlcmd prints when the identity is refused (`denied`) and when the server does not answer (`down`), and for the gate: the program (`cli`), how a command names one connection (`match`: the server and port after `-S`), where the statements are (`input`: `-Q`, `-i`, `:r`), how a call names its server (`pin`: `-S` and `--server`, the spellings that are certainly the same place, `-D` and the go-sqlcmd subcommands that name no server), the three lists (`reads`, `writes`, `refuse`), the verbs and the rules.
- `rules.json`: `sqlserver-other`, the other ways to a SQL Server: the programs `bcp`, `Invoke-Sqlcmd`, `isql`, `usql`, `mssql-cli`, and the words `pyodbc`, `pymssql`, `mssql`, `tedious` in a one-line `python -c` or `node -e`. The gate cannot judge them, so each is refused and the agent is told to use `sqlcmd` with a connection. A script file that imports such a library stays a blind spot.
- `launch/start-vscode.cmd`: `runas /netonly` with the account the person types, then VS Code. Kept for a team that does not save identities; Get ready's **Open VS Code with identities** does the same without a prompt.
- `skills/sqlserver-jobs/`: a sample skill (start a job, wait for it with `harness wait`, check it).

The connections themselves are not in the pack: `../../examples/connections.json` lists three made-up ones (`orders-dev`, `orders-ist`, `orders-qat`).

**Which server.** A call of `sqlcmd` is judged only when it names exactly one server with `-S` (or `--server`) and that server, written any case, with `tcp:` in front, as `host:port`, with a dot after the host or zeros in front of the port, is the address of a connection. Anything else is refused, whatever it says, with the way: `harness connections find <words>` and the server as the connection gives it (`127.0.0.1` is not `localhost`; no name is looked up). That covers no `-S` (the default server, `SQLCMDSERVER`, `-D`), two `-S`, a server the line does not show (`$(...)`, a variable, an array) and the go-sqlcmd subcommands (`sqlcmd query ...`). `sqlcmd -?`, `--help` and `--version` need no server. With no connection of this type at all (the list is empty, or has other types; the pack is off) every call of `sqlcmd` is refused with the way, except those three. A `DROP` is refused with its own reason before the server is looked at. A script that another command of the same line can change (`cp x.sql y.sql && sqlcmd -i y.sql`) is refused: change the file and run sqlcmd as two calls.

The gate answers a call to SQL Server one of three ways. It cuts the text of `-Q` (and every script file: `-i`, and the files it names with `:r`) into statements and judges each by the lists of the type.

- **Runs, no question (`reads`).** Only what the gate can show to be a read: `SELECT` without `INTO`, `WITH ... SELECT`, `USE`, `SET` options (`NOCOUNT`, `ANSI_*`, `QUOTED_IDENTIFIER`, ...), `PRINT`, `DECLARE @x <type>`, `SET @x = <constant>` and the read-only system procedures (`sp_help`, `sp_helptext`, `sp_columns`, `sp_tables`, and a few like them). Every statement of the call must be on the list. A word after the first words does not help: a read that hides an `UPDATE` in its tail is not a read.
- **Runs on a connection you opened (`writes`).** `INSERT INTO`, `UPDATE ... SET ... WHERE`, `DELETE FROM ... WHERE` (the `WHERE` must stand outside every parenthesis, and not be true whatever the row holds: `1=1`, `(1=1)`, `1<2`, `NOT 1=0`, `'a'='a'`, `col=col`; this is a guard against a slip, **not a boundary**: `WHERE id > 0` passes), `MERGE`, `CREATE` or `ALTER` of a `PROCEDURE`, `VIEW` or `FUNCTION` (one statement to the end of its batch, `GO` ends it; deploying it runs nothing of its body, so the refuse list does not read the body: a `DROP`, a `TRUNCATE` or `EXEC(@sql)` in it waits for you like any deploy; a body with `xp_...`, `KILL`, `SHUTDOWN`, `RESTORE`, `RECONFIGURE`, `OPENROWSET` or `BULK` is on no list and always asks; a `TRIGGER` asks), `EXEC <proc>` with plain parameters (with or without a schema; not `sp_` or `xp_`), `CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE ... ADD`, `BEGIN TRAN`, `COMMIT`, `ROLLBACK`, `SELECT ... INTO #temp`, and the drops of a test: `DROP TABLE`, `TRUNCATE TABLE`, `DROP PROCEDURE` (or `VIEW`, `FUNCTION`, `TRIGGER`, `SYNONYM`) with or without `IF EXISTS`, and `IF OBJECT_ID('...') IS NOT NULL DROP ...`. The type's `open` word says how far a person may open a connection for one task (the button **Open <connection> for this task** on the card of a held call): `all` in DEV and IST, `no` in QAT and PROD. A call with a statement on neither list is not passed by an open connection, and its card has no Open button.
- **Drops by environment (`rules`).** A drop of a table or a truncate is a destroy: on DEV and IST it waits for you (and an opened connection passes it); on QAT and prod it is refused. A temporary table (`#t`) and a code object (a procedure, view, function) are no destroy: dropping them loses no data, so they are an ordinary write, also on QAT.
- **Refused at once, with the right way (`refuse`).** `KILL`, `SHUTDOWN`, `RESTORE`; sqlcmd's `!!` (a shell command), `:connect`, `:out`, `:error`, `:perftrace`; `xp_` procedures such as `xp_cmdshell` outside the body of a procedure. Each reason says what to do instead. A company's `rules` and an open connection do not change this.
- **Script variables are filled in.** A `:setvar` line and `sqlcmd -v name=value` give `$(name)` its value before the statements are judged, as sqlcmd does (an SSDT publish script works this way), so the gate judges the statements that run. A `$(name)` that nothing fills asks.
- **Everything else asks you, also on an opened connection.** A write with no `WHERE`, `SELECT ... INTO` a table that is not `#temp`, a string run as SQL (`EXEC('...')`, `sp_executesql`: the gate cannot see the statement, you can on the card), `BACKUP`, `DBCC`, `RECONFIGURE`, `GRANT`, `DENY`, a trigger switch, `OPENROWSET`, `WAITFOR`, any other procedure, a script the gate cannot read, a text with a shell variable in it, a call with no `-Q` and no `-i` (sqlcmd then reads its input), and a call with `-o` or `-q` or `SQLCMDINI=`. The card says why it waits (**Why held**). On QAT, procedures are the person's to run; on prod only reads run.

**Why the refuse list is short.** An agent testing ETL on DEV drops and fills tables, deploys procedures that drop temporary tables and build SQL in strings, and runs SSDT scripts full of `:setvar`. When all of this was refused, the agent had no way on: it stopped and the task stalled. A refusal is only right when the agent has a right way it can take by itself (name the server, run the shell command in the terminal, redirect the output there). Where the only right way is a person's judgment, the call waits for that person instead. Nothing on this list passes unasked that did not before, except on a connection you opened.

The refuse list is best effort: it catches the plain spellings and a spelling it misses lands in "asks you", not in "runs". **The final guarantee is the rights of the account.** Use an account for DEV that cannot drop tables, and a read-only account where a task only reads: then no text can do more than the account may. When you change the lists, keep the rows of `.harness/tests/test_gate_sqlserver.py` and `test_gate_redteam.py` as the start of your own.

## To use it

1. **Turn on**: name it in `<knowledge base>/company/tools/packs.json` (`{"use": ["sqlserver"]}`), and put your connections in `company/tools/connections.json` (the form: `.harness/contracts/toolpack/connections.md`). Import the knowledge base in Get ready, or run `harness company sync`.
2. **Set up**: Get ready, Local: the folder of `sqlcmd` when it is not on the PATH.
3. **Sign in**: Connections & sign-ins: each colleague presses **Sign in** on a connection, types the account (`DOMAIN\id` for `windows`) and the password, and **Sign in** tests it and keeps it when the test passes. The identity stays in `.harness/.env` on that computer.
4. **Try**: **Open VS Code with identities**, tick the connections for that window. With two different Windows accounts (one for DEV, one for IST), the window holds one; the other is reached through `harness as <name> -- sqlcmd -S <its server> ...` (the prefix gives the sign-in, not the server; `harness connections find <name>` prints the call), which the agent is told at the start of each chat.

Before colleagues use it, show them *What the agent can do on your connections* in `docs/03-configure.md`: the agent has their account's rights, reads run, writes wait for them, and what Open to the agent changes.
