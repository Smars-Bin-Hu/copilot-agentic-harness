# 检查：批准之后的那一轮为什么贵（只出数字）

背景：公司电脑上一个真任务里，隔 6–16 分钟才批准的那几次，批准后的一轮花了 79–96；隔 2–3 分钟批准的只花 12–23。在开发用的 Mac 上，“离上一次调用超过 5 分钟，整段上下文按写缓存的价重付”这条线量得很清楚，但 Mac 上冷回来一次只有 13–16，而且照片里有一行解释不了：同一个批准码 32 秒后又发了一次，那一条仍花了 77.6。这次检查在公司电脑上读 Copilot 自己的会话记录，把那几轮每一次调用的缓存读写打出来。

## 这个脚本做什么，不做什么

- 只读 `%USERPROFILE%\.copilot\session-state\` 下每个会话的 `events.jsonl`。
- 不调用模型，不联网，不写任何文件，不花 credits。
- 只打印个数、秒数、token 数和 credits。
- 不打印文件名、路径、会话编号、工具的名字、模型的具体编号，也不打印任何对话内容。它只看一条消息开头的几个词，用来认出这是看板的哪一种固定消息（批准后的那条、stop hook 的那条、go on），打印的是种类的名字。
- Python 3.9 就能跑，只用标准库。

## 步骤

1. 在 GitHub 上打开这个分支的 `checks/2026-11-26-approval-cost.py`，存到公司电脑上任意一个文件夹。不用放进 harness 的文件夹。
2. 在 PowerShell 里进到那个文件夹，把窗口拉到最宽（一行约 130 个字符），运行：

   ```powershell
   python .\2026-11-26-approval-cost.py
   ```

   `python` 找不到时改用 `py -3 .\2026-11-26-approval-cost.py`。它看最近 7 天。那个任务如果已经是 7 天以前的，加 `--days 14`。
3. 输出分 10 段，约 70 到 140 行。拍照或截图发回，一屏放不下就分几张。**第 5、6、7、9 段最要紧**，这四段每一行都要拍清楚。
4. 第 9 段显示的是“批准次数最多的那个 chat”的每一轮。如果它不是照片里那个任务（看轮数和批准次数对不对），再跑一次 `--chat 2`（第二多的），只拍第 9 段。
5. 记下从回车到出完用了多久。

## 出了问题

- 报错：把报错那一屏拍照发回，不用自己修。
- 只有一行 `no priced Claude usage records found`：最近几天的记录里没有 Claude 的计价信息。也拍照发回，再试 `--days 30`。

## 发回来以后看什么

| 段 | 回答什么问题 |
| --- | --- |
| 2 | 公司电脑上 5 分钟这条线是不是一样清楚；冷回来一次写多少 token、花多少。“等完之后的第一次调用”占这些轮花费的百分之几 |
| 3 | 批准后的那条、stop hook 的那条、go on 各开了多少轮，各花多少 |
| 4 | 人实际隔多久才批准：1 分钟内、5 分钟内、半小时内、更久各多少次，各花多少 |
| 5 | **第二个原因有没有**：离上一次调用不到 4 分钟、缓存却没用上的轮。每行最后写着和上一次调用比什么变了（模型、给的工具数、工具定义的大小、思考强度、窗口大小）。这里是 0，就只有“超过 5 分钟”一个原因 |
| 6 | **32 秒重发的那一对**：两条各自的第一次调用读了多少缓存、写了多少；第二条来的时候第一轮结束了没有 |
| 7 | **轮内等冷了几次，是在等什么**：同一轮里，离上一次调用超过 5 分钟才来的调用有多少次、几次是冷的；按中间跑得最久的那个工具调用分成五种（`wait-approval` 等批准、`wait-run` 等外部系统、`sub-agent`、`question` 提问、`other`），各花多少；最贵的 12 次各一行 |
| 8 | stop hook 拦了多少次；它开的轮里最贵的三轮是不是因为真干了活（看模型调用数、工具调用数、子 agent 的花费） |
| 9 | 那个任务的每一轮：上下文多大（决定冷回来一次多少钱）、开头冷不冷、轮内冷了几次花了多少（`ci` 后面的两个数）。能和那个任务 Time and usage 记录里的 32 行逐行对上 |
| 10 | 单价、缓存寿命、思考强度 |

同一个脚本在开发用的 Mac 上跑过（看了 40 天），输出留着用来对照。Mac 上第 5 段有 2 行：一行是给的工具数变了（60 变 79），缓存整段没用上；这说明“工具列表一变，缓存就废”是真的会发生的第二个原因。
